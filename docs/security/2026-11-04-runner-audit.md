# runner 보안 점검 (2026-11-04)

- 범위: 코드 실행기 `runner`(Java·Python)와 judge의 결과 처리. 사용자가 임의의 코드를 제출할 수 있다는 전제에서 히든 데이터 노출, 판정 조작, 다른 사용자 간섭, 외부 접근을 확인했다.
- 방법: main(`274e529`)의 `docker/runner.Dockerfile` 이미지를 운영 compose와 같은 옵션(`read_only`, capability 6개, `no-new-privileges`, 메모리 1.5GB, CPU 2, PID 512, `RUN_SLOTS=2`, `/tmp` tmpfs)으로 로컬에서 띄우고 runner `/run`에 직접 요청했다. 운영 서버(pahidc)와 운영 데이터는 사용하지 않았다.
- 상태: **코드 수정 완료, 운영 배포·확인 대기**(브랜치 `fix/runner-hardening`). 운영 확인은 [인수인계](../handoff-runner-hardening.md). 남은 강화는 [0012](../decisions/0012-runner-fast-concurrent-secure.md) 4.3 B(샌드박스 엔진).

## 상세

### F1. 히든 테스트셋 캐시를 사용자 코드가 읽는다 — 높음

- 결과: 테스트셋을 runner에 올린 뒤, 함수형 Python 코드가 캐시 폴더의 파일을 읽어 반환하자 기댓값까지 그대로 나왔다. runner에 캐시된 모든 문제(용량 한도 200MB까지)가 대상이다.
- 원인: `runner/server.py` `store_testset`이 `TESTSET_DIR`(기본 `/tmp/testsets`)를 root의 기본 umask(022)로 만든다. 폴더 755·파일 644라서 샌드박스 uid(10001)도 읽을 수 있다. 사용자 코드와 캐시가 같은 `/tmp`에 있다.
- 영향: 정답 하드코딩으로 모든 문제를 통과할 수 있다. 문제 데이터(히든 케이스)는 공개하지 않는 자산이다.
- 수정:
  1. 즉시: 캐시 폴더 `0700`, 파일 `0600`(서버 시작 시 `os.umask(0o077)`), 이미 있는 캐시도 권한을 고친다.
  2. 캐시를 사용자 코드가 쓰는 `/tmp` 밖의 서버 전용 경로로 옮긴다(별도 tmpfs).
  3. 이후 실행마다 마운트 네임스페이스를 나눠 캐시가 아예 보이지 않게 한다(0012 4.2·4.3).
  4. `runner/selftest.py`에 "샌드박스 uid로 테스트셋 파일 열기 실패" 검사를 더한다.
- 노출 여부: runner는 파일 접근 로그를 남기지 않아 과거 악용 여부를 확인할 수 없다. 중요한 문제부터 히든 케이스 교체를 검토한다.

### F2. 제출 결과의 stderr로 히든 입력이 나간다 — 높음

- 결과: 히든 테스트셋으로 채점할 때 사용자 코드가 인자를 담은 예외를 던지면, 역추적과 함께 입력값이 결과 `stderr`에 담겼다.
- 원인: judge `apps/judge/src/jobs.ts` `trimResult`가 제출(submit)에서도 `stderr`를 케이스당 2000자까지 남긴다. 화면(`ResultPanel.tsx`)은 히든 케이스의 상세를 보여 주지 않지만, `GET /api/submissions/:id` 응답에는 있다.
- 영향: 케이스당 최대 2000자, 히든 케이스 최대 200개의 입력을 제출 한 번에 얻을 수 있다. F1을 고쳐도 이 경로로 입력이 샌다.
- 수정: 제출에서는 stderr를 오류 유형(런타임 에러·메모리 초과·시간 초과, 필요하면 예외 클래스 이름까지)으로만 바꾸고 원문은 judge 로그에만 남긴다. `packages/shared`의 계약을 바꾸고 api·web을 맞춘다. 같은 이유로 제출의 `actual`·`stdout` 제거(지금 동작)를 계속 유지한다.

### F3. 함수형 시간 초과 판정 조작 — 중간

- 결과: 시간 제한 1초 문제에서 약 1.6초 걸리는 코드가, 시간 측정 함수를 바꿔치기하자 `pass`, `timeMs: 0`으로 판정됐다(같은 코드를 그대로 내면 `timeout`).
- 원인: `runner/server.py` `_judge_value`가 하네스(사용자 코드와 같은 프로세스)가 보고한 `timeMs`로 시간 초과를 정한다. 바깥의 벽시계 제한은 제한 + 여유(Python 1초, Java 3초)라 그 범위 안에서 우회된다. Java도 같은 구조다.
- 영향: 효율성 문제에서 시간 제한을 최대 여유만큼 늘려 통과할 수 있다.
- 수정: 시간 초과 판정은 runner가 바깥에서 잰 값(자식 프로세스의 `wait4` rusage CPU 시간, 또는 벽시계에서 기동 기준값을 뺀 값)으로 한다. 하네스가 보고한 값은 화면 표시용으로만 쓴다. 메모리는 지금처럼 바깥 측정(`ru_maxrss`)을 쓴다. 원칙: **비신뢰 프로세스가 만든 값은 정답 비교용 반환값 외에는 판정에 쓰지 않는다.**

### F4. 다른 사용자의 소스 코드 읽기 — 중간

- 결과: 두 요청을 동시에 실행했을 때, 한쪽 코드가 다른 쪽 작업 폴더의 `solution.py`를 읽었다.
- 원인: 모든 실행이 같은 uid(10001)로 돈다. 작업 폴더를 `0700`으로 만들어도 소유자가 같아 서로 읽을 수 있다.
- 영향: 동시에 채점되는 다른 사용자의 풀이(개인 데이터) 노출, 풀이 표절.
- 수정: 슬롯마다 다른 uid(예: 10001+슬롯 번호)로 실행하고 작업 폴더를 그 uid 소유 `0700`으로 만든다. 이후 실행마다 마운트·PID 네임스페이스를 나눈다(0012 4.3).

### F5. 다른 사용자의 프로세스 종료 — 중간

- 결과: 한쪽 코드가 같은 uid의 모든 프로세스에 종료 신호를 보내자, 동시에 실행 중이던 다른 요청이 강제 종료되고 "프로세스가 강제 종료되었습니다(메모리 초과 가능)"로 오판정됐다.
- 원인: F4와 같다(같은 uid). `RLIMIT_NPROC`도 uid 단위라 한 사용자의 fork 폭탄이 다른 사용자의 프로세스 생성을 막을 수 있다.
- 영향: 다른 사용자 채점 방해, 잘못된 판정.
- 수정: F4의 슬롯별 uid로 해결한다. `RLIMIT_NPROC`을 uid별로 작게(Python은 사용자 코드가 프로세스를 만들 필요가 없고, Java는 JVM 스레드 수만큼) 둔다.

### F6. 사용자 코드에서 runner API 접속 — 낮음~중간

- 결과: 사용자 코드가 `127.0.0.1:8000`(runner API)에 접속해 응답을 받았다. 운영 구조에서는 같은 `sandbox` 네트워크의 judge(8790)에도 닿는다.
- 원인: 사용자 프로세스가 runner 서버와 같은 네트워크 네임스페이스에 있고, runner API에 인증이 없다.
- 영향: judge의 API는 HMAC 서명이 필요해 직접 피해는 작다. runner API로는 다른 실행을 겹쳐 요청하거나(슬롯 소모), 캐시를 채워 다른 테스트셋을 밀어낼 수 있다. 실행 id가 UUID라 다른 작업의 중지는 사실상 어렵다.
- 수정: runner API에 judge와 공유하는 토큰을 요구한다(root만 읽는 파일). 샌드박스 uid의 네트워크를 막는다(실행마다 네트워크 네임스페이스, 또는 시작 시 uid 기준 방화벽 규칙을 넣고 `NET_ADMIN`을 버린다).

## 수정 순서

1. F1·F2: 작은 변경이라 바로 배포한다. 히든 케이스 교체를 검토한다.
2. F3: 판정 기준이 바뀌므로 기존 판정과 비교(그림자 채점)한 뒤 켠다.
3. F4·F5: 슬롯별 uid. F6: API 토큰과 네트워크 차단.
4. 항목마다 `runner/selftest.py` 회귀 검사를 더하고 CI `docker` 잡에서 통과시킨다.
5. C++ 지원(0012 3.5)은 1~3을 마친 뒤 연다. C++는 언어 차원의 보호가 없어 위 통제에 전적으로 기댄다.

## 다시 점검할 때

- 같은 방법(운영 옵션의 runner 이미지 + `/run` 직접 요청)으로 F1~F6을 다시 확인하고 이 문서의 상태를 바꾼다.
- 0012의 워밍 실행기·C++·샌드박스 엔진(nsjail/gVisor)을 들일 때마다 같은 항목을 다시 확인한다.

## 수정 내용 (fix/runner-hardening)

| # | 수정 | 확인 |
|---|---|---|
| F1 | 캐시를 `/var/cache/solveline-testsets`(별도 tmpfs, 0700)로 옮기고 폴더 0700·파일 0600으로 만든다. 시작할 때 기존 캐시 권한도 고친다(`runner/server.py` `store_testset`·`secure_testsets`) | 같은 재현에서 사용자 코드가 아무것도 읽지 못함. selftest "testset cache root only" |
| F2 | 제출 결과의 stderr를 오류 종류로만 바꾼다(`packages/shared` `submitErrorSummary`·`redactSubmitResult`). judge가 저장 전에, API가 돌려주기 전에(예전 기록 포함) 적용 | `apps/judge/test/hardening.test.ts`, `apps/api/test/app.test.ts` |
| F3 | 바깥에서 잰 시간(벽시계·CPU 중 작은 값 − 기동 기준값)이 제한 + 여유(150ms + 인자 1MB당 200ms)를 넘으면 시간 초과. 하네스 값은 형식을 검사하고 표시에만 쓴다 | 같은 재현에서 `timeout`. selftest "startup baseline measured", 기존 "time limit excludes JVM startup" 통과 |
| F4·F5 | 슬롯마다 다른 uid(10002~), uid당 프로세스 128, 작업이 끝나면 그 uid의 남은 프로세스·파일 정리 | 같은 재현에서 다른 작업의 소스를 못 읽고, 다른 작업이 정상 종료. selftest "concurrent jobs use different uids" |
| F6 | runner를 `network_mode: none`으로 두고 공유 볼륨의 unix 소켓(root:1000 0660)으로만 받는다. judge는 `RUNNER_URLS=unix:…` | 루프백 TCP 닫힘, 샌드박스 uid는 소켓 접속 거부, gid 1000만 응답. selftest "runner socket 0660 root:judge" |

판정이 바뀔 수 있는 점: 함수형에서 모듈 최상위 코드(전처리)와 인자 파싱도 바깥 시간에 들어간다. 제한에 아주 가까운 풀이는 여유(150ms + 인자 크기)를 넘으면 시간 초과가 될 수 있다.
