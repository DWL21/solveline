# 테스트 전략

## 1. 원칙

좋은 테스트에 대한 기준은 새로 만들지 않고, 검증된 생각을 그대로 따른다.

- **테스트는 빠른 피드백을 위한 것** — 켄트 백(Kent Beck)이 TDD에서 강조하듯 작은 단계로 실패하는 테스트를 먼저 쓰고, 통과시키고, 정리한다(빨강 → 초록 → 리팩터링). 이번에 정적 분석이 찾은 백업 정리 버그도 실패하는 테스트를 먼저 쓰고 고쳤다(`apps/api/test/backup.test.ts`).
- **테스트가 갖춰야 할 성질** — 켄트 백의 *Test Desiderata*에서 가져온 기준으로 리뷰한다.
  - 격리되어 있다(isolated): 테스트마다 새 사용자·새 데이터, 순서에 의존하지 않는다
  - 결정적이다(deterministic): 고정 대기 대신 조건을 기다린다(`expect.poll`, web-first assertion)
  - 빠르다(fast): 같은 위험이면 낮은 층(단위·API)에서 잡는다
  - 동작에 민감하고 구조에 둔감하다(behavioral, structure-insensitive): DOM 속성 대신 사용자가 보는 결과로 확인한다 — 예) 비회원 에디터는 `contenteditable` 값이 아니라 "입력해도 코드가 바뀌지 않는다"로 검사
  - 읽기 쉽고 구체적이다(readable, specific): 테스트 이름이 곧 명세, 실패 메시지가 원인을 가리킨다
- **자가 테스트 코드(Self-Testing Code)와 지속적 통합** — 마틴 파울러(Martin Fowler)가 말하듯 테스트가 코드와 함께 있고 모든 변경마다 자동으로 돌아야 한다. 메인 브랜치는 언제나 통과 상태를 유지하고, 깨지면 가장 먼저 고친다.
- **테스트 피라미드(Practical Test Pyramid)** — 위로 갈수록 느리고 깨지기 쉬우므로 수를 줄인다. 넓은(broad-stack) 테스트는 핵심 사용자 여정만, 세부 규칙은 아래층에서.
- **비결정적 테스트는 즉시 격리한다** — 파울러의 *Eradicating Non-Determinism in Tests*처럼, 가끔 실패하는 테스트는 신뢰를 갉아먹는다. 재시도로 통과한 테스트는 "불안정"으로 리포트에 드러내고 원인을 고친다(6절).
- **단순하게** — 테스트 코드도 제품 코드다. 중복을 줄이되(페이지 객체·데이터 빌더) 의도를 숨기지 않는다.

## 2. 테스트 피라미드와 책임

| 층 | 도구 | 무엇을 | 수 | 실행 |
|---|---|---|---|---|
| 단위·통합(인메모리) | Vitest | 저장소·권한·마이그레이션·설정 검증·순수 함수. 앱을 프로세스 안에서 요청 단위로 호출 | 61+ | 모든 커밋, ~5초 |
| runner 자체 검사 | Python | 격리(네트워크 차단·권한), 시간 제한, 큰 정수, 언어별 실행기 | 30+ | 이미지 빌드마다 |
| API 블랙박스 | Playwright `request` | 실제 이미지(nginx → api → runner)를 HTTP로: 계약, 권한 결정표, 채점 상태 전이, 경계값, 데이터 분리 | 59 | 모든 PR, ~30초 |
| UI E2E | Playwright 브라우저 | 핵심 여정만: 둘러보기·풀기·제출·자동 저장·편집 모드·관리자·반응형·접근성 | 21 | 모든 PR, ~30초 |
| 운영 스모크 | Playwright | 운영 사이트 읽기 전용 건강 신호 | 4 | 매일 |
| 정적 분석 | SonarQube | 버그·취약점·코드 스멜·중복·커버리지 → 품질 게이트 | — | 모든 PR |

## 3. 위험 기반 범위

| 위험 | 영향 | 막는 곳 |
|---|---|---|
| 남의 데이터가 보이거나 바뀜(사용자 분리) | 매우 큼 | 단위 + API(`isolation.spec`) |
| 권한 없는 사용자가 공용 문제·컬렉션을 바꿈 | 큼 | API 결정표(`permissions.spec`) |
| 채점이 틀림(판정·점수·시간 제한) | 매우 큼 | runner 자체 검사 + API(`judge.spec`) |
| 히든 케이스 유출 | 큼 | API(채점 결과에 반환값 없음) |
| 작성한 코드가 사라짐 | 큼 | 단위(임시 저장 큐) + UI(자동 저장 후 새로고침) |
| 휴대폰에서 못 씀 | 중간 | UI(@mobile·@tablet 프로젝트, 가로 넘침 검사) |
| 접근성 저하 | 중간 | axe(critical 차단, 나머지 추세) |
| 배포 뒤 핵심 경로 장애 | 큼 | 운영 스모크 + 배포 헬스 체크 |

## 4. 설계 기법

| 기법 | 적용 |
|---|---|
| 결정표(Decision Table) | 역할(비회원·사용자·편집 권한·마스터) × 기능 → 기대 상태 코드. 표 한 줄이 테스트 하나(`permissions.spec`) |
| 상태 전이(State Transition) | 제출 queued → running → done·error·cancelled, 되돌아가지 않음(`judge.spec`) |
| 동등 분할(Equivalence Partitioning) | 판정 종류(정답·오답·컴파일 오류·런타임 오류·시간 초과·표준 출력)마다 대표 하나, Java·Python 각각 |
| 경계값 분석(Boundary Value) | 시간 제한 99·100·10000·10001ms, 2^53 넘는 정수 |
| 계약 테스트(Consumer-side Contract) | 모든 응답을 앱과 같은 Zod 계약으로 검증, 오류 봉투 `{ error: { code, message } }` |
| 사용자 여정(Journey) | 열기 → 작성 → 실행 → 제출 → 맞힘 표시 |
| 탐색적 테스트 | 새 기능은 자동화 전에 실제 기기(아이폰·갤럭시)로 30분 탐색, 찾은 결함은 재현 테스트로 남긴다 |

## 5. 환경과 데이터

- **테스트 환경은 운영과 같은 이미지**(`compose.test.yaml`): runner·api는 운영 이미지와 같은 격리 옵션, 웹은 운영의 Pages + API 게이트웨이와 같은 출처 구성을 nginx 하나로 재현한다. 데이터는 tmpfs라 매번 빈 상태.
- **비밀 값은 실행마다 새로**(`scripts/test-env.sh`가 `e2e/.env.local`에 생성, 커밋 금지).
- **테스트 전용 로그인**(`POST /api/test/session`): Google 왕복 없이 역할별 세션을 만든다. `TEST_AUTH_TOKEN`이 있을 때만 경로가 생기고, 운영(`NODE_ENV=production`)에서 설정하면 서버가 시작하지 않는다(단위 테스트로 보장).
- **데이터는 테스트가 직접 만든다**: 공유 픽스처 대신 데이터 빌더(`aProblem()`)로 필요한 것만 드러내고, 사용자 이메일은 테스트마다 고유. 병렬 실행·재실행에 안전하다.

## 6. 불안정(flaky) 테스트 정책

1. CI에서만 재시도 2회. 재시도로 통과하면 **불안정**으로 집계되어 품질 리포트에 이름이 나온다.
2. 불안정 테스트는 그 주 안에 원인을 고친다: 고정 대기 → 조건 대기, 공유 데이터 → 고유 데이터, 애니메이션·시간 → 명시적 기다림.
3. 바로 못 고치면 `test.fixme`로 격리하고 이슈를 연다(격리 목록은 리포트에서 0을 목표로 관리).
4. 실패 분석 자료: trace·스크린샷·영상(실패 시만), 서버 로그(`scripts/test-env.sh logs`).

## 7. 진입·종료 기준(PR)

- **진입**: 타입 검사 통과, 변경에 맞는 테스트 포함(버그 수정은 재현 테스트 먼저).
- **종료(머지 조건)**: 단위·API·UI 전부 통과, 커버리지 래칫 이상, SonarQube 품질 게이트 OK, 새 불안정 테스트 0, 접근성 critical 0.
