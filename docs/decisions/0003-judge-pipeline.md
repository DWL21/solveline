# 0003. 채점 파이프라인: 제출 큐 · 테스트셋 분리 · 실행기 확장

- 날짜: 2026-10-22
- 상태: 1단계 채택, 2단계(샌드박스 엔진 교체)는 보류

## 배경

지금 구조(0001):

```
브라우저 ──POST /api/run (코드 + 모든 케이스)──▶ api ──동기 HTTP──▶ runner 1대 ──케이스마다 프로세스
```

문제점

1. **동기 한 번에 끝난다.** 채점이 길면 Cloudflare 응답 제한(100초)에 걸려 runner가 80초에서 나머지를 건너뛴다. 요청이 몰리면 줄을 설 곳이 없다.
2. **runner를 늘릴 수 없다.** api가 runner 주소 하나만 안다.
3. **테스트 데이터가 문제 본문에 있다.** 히든 케이스가 문제 JSON 안에 있어, 0.3초마다 도는 자동 저장이 수백 KB를 보낸다. 그래서 효율성 테스트 크기를 필드당 20만 자로 줄였다. 기존처럼 수만 문제·큰 데이터를 담을 수 없다.
4. **DB 백업이 없다.**

## 다른 저지 검토

| | 기존(기존) | 기존 | Judge0 / go-judge / isolate (오픈소스) |
|---|---|---|---|
| 큐 | 큐 4개(우선순위별 FIFO). 채점 프로그램은 번호가 작은 큐부터 확인하며, 어떤 큐를 볼지 실행 시 정한다 | 공개 자료 없음 | Judge0: API 서버 + 작업 큐 + 워커, 결과는 폴링/웹훅 |
| 실행기 | 채점 서버 1대가 한 번에 제출 1개만 채점, 서버 수는 유동적 (AWS EC2 c4.large) | 공개 자료 없음. 화면상 테스트마다 시간·메모리를 따로 보여 줌 | go-judge: 실행 서비스(REST/gRPC), 환경 풀, 업로드 파일 캐시(fileId). isolate: 네임스페이스 + cgroup 샌드박스(CMS 등) |
| 격리 | 공개 자료 부족 | 공개 자료 없음 | 네임스페이스 · cgroup(메모리·CPU·프로세스 수) · seccomp |
| 정답 판정 | 스페셜 저지(검증 코드) 지원 | 반환값 비교 | 저지마다 다름 |

기존 내용은 서비스 종료(2026-04-28) 전 도움말(help.기존.net의 채점 큐·채점 정보 문서)을 기준으로 했다. 기존는 아키텍처를 공개한 자료를 찾지 못해 추측하지 않는다.

공통점: **① 제출을 큐에 넣고 ② 상태 없는 실행기 여러 대가 하나씩 꺼내 채점하며 ③ 테스트 데이터는 실행기 쪽에 캐시한다.** 이 세 가지를 1단계로 들여온다.

## 결정 (1단계)

```
브라우저 ─POST /api/submissions─▶ api ─INSERT─▶ submissions(queued)
   ▲                                │
   └── GET /api/submissions/:id ◀───┤ 디스패처: 우선순위(코드 실행 > 제출) → 빈 runner 슬롯
                                    ▼
                         runner A, B, … (RUNNER_URLS)
                         └ 테스트셋 캐시(해시) — 없을 때만 받음
```

1. **제출 큐**: `submissions` 표에 넣고 id를 바로 돌려준다(202). api 안의 디스패처가 우선순위 순으로 꺼내 runner 슬롯에 보낸다. 브라우저는 id로 결과를 조회한다(폴링). HTTP 하나가 채점 시간을 붙잡지 않으므로 Cloudflare 제한과 무관해진다. api 재시작 시 `running`으로 남은 제출은 다시 `queued`로 돌린다.
2. **실행기 확장**: `RUNNER_URLS`(쉼표 구분)와 runner별 슬롯 수만큼 동시에 보낸다. 서버를 늘리면 runner만 더 띄운다. 계정이 생겨도 디스패처·큐 구조는 같다.
3. **테스트셋 분리**: 히든 케이스는 내용의 SHA-256으로 이름 붙인 파일(`DATA_DIR/testsets/<hash>.json`)에 둔다. 같은 내용은 한 번만 저장한다. 문제 본문에는 `hiddenTestset: { hash, count }`만 남아 자동 저장이 가벼워진다. 편집은 별도 API로 한다.
4. **runner 테스트셋 캐시**: 디스패처는 해시만 보낸다. runner는 `/tmp/testsets`에 해시별로 캐시(용량 상한, 오래된 것부터 삭제)하고, 없으면 `409 testset_missing`으로 알려 디스패처가 내용을 한 번 올린다(go-judge의 파일 캐시와 같은 방식).
5. **큰 정수 보존**: 리터럴은 텍스트로 넘기고 runner(Python)가 해석한다(#13).
6. **백업**: api가 매일 SQLite 온라인 백업(`db.backup`)과 테스트셋 묶음을 `DATA_DIR/backups`에 만들고 7일치를 남긴다.

검토 후 뺀 것: **Java AppCDS**. JDK 클래스는 기본 CDS 아카이브(`-Xshare:auto`)가 이미 덜어 주고, 앱 아카이브는 클래스패스가 같아야 하는데 사용자 `Solution`이 실행마다 다른 작업 폴더에 있어 이득(실행기 클래스 1개)에 비해 깨지기 쉽다.

## 보류 (2단계 이후)

- **샌드박스 엔진 교체(go-judge 또는 isolate)**: 실행마다 cgroup v2로 메모리·CPU를 정확히 재고 seccomp를 걸 수 있다. pahidc는 cgroup v2(systemd)라 가능하지만, Docker 안에서 돌리려면 보통 `--privileged`가 필요해 지금의 최소 권한 runner보다 호스트 노출이 커진다. 계정을 열기 전(다른 사람의 코드를 받기 전)에 따로 결정한다.
- **여러 계정 / 기존 이식 단계**: SQLite → PostgreSQL, 테스트셋 파일 → 객체 저장소(R2/S3) + runner 캐시, 큐 → Redis Streams 등 외부 큐, 스페셜 저지(검증 코드), 언어별 시간 배수, 채점 호스트 분리.

## 결과

- 긴 채점도 끊기지 않고, 코드 실행이 제출 채점 뒤에 밀리지 않는다.
- 자동 저장 본문에서 히든 데이터가 빠진다. 효율성 테스트 크기 상한은 요청 크기가 아니라 runner 캐시 용량과 디스크가 정한다.
- runner를 늘리는 것만으로 처리량을 늘릴 수 있다.
- 디스패처가 api 프로세스 안에 있으므로 api는 아직 1대여야 한다(여러 대가 되면 외부 큐로 옮긴다).
