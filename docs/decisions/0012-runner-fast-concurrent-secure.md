# 0012. 실행기(runner) 개편: 빠르게 · 동시에 · 가볍게, 그리고 코드 실행 보안

- 날짜: 2026-11-04
- 상태: 제안(검토 전). [0011](0011-judge-queue-scaling.md)(대기열·오토스케일링)의 실행 층을 다룬다. [0001](0001-sandbox-and-access.md)·[0003](0003-judge-pipeline.md)의 샌드박스 보류 항목을 다시 연다.
- 2026-11-04 보안 점검 결과: [docs/security/2026-11-04-runner-audit.md](../security/2026-11-04-runner-audit.md). 이 문서의 4장·6장 1~3단계가 그 수정 계획이다.

## 1. 지금 비용 (측정)

운영 runner 이미지와 같은 옵션(`read_only`, 최소 capability, `cpus: 2`, 1.5GB)으로 띄운 컨테이너에서 쟀다. 측정 호스트는 4 vCPU 클라우드 컨테이너(pahidc 아님), 값은 중앙값이다.

| 단계 | Java | Python |
|---|---|---|
| 컴파일(요청마다 새 `javac` JVM / `py_compile` 프로세스) | 약 480ms | 약 40ms |
| 케이스마다 새 프로세스(함수형) | 약 67ms | 약 38ms |
| 케이스마다 새 프로세스(입출력형) | 약 75ms | 약 16ms |
| **히든 200개 제출의 고정 비용** | **약 14초** | **약 7.6초** |

사용자 코드가 1ms에 끝나도 제출 하나가 슬롯을 수 초씩 붙잡는다. 0011의 평균 실행 시간 S̄ 대부분이 이 고정 비용이다.

같은 컨테이너에서 시제품으로 잰 대안:

| 대안 | 측정값 | 지금 대비 |
|---|---|---|
| 계속 떠 있는 JVM의 `javax.tools` 컴파일(예열 후) | 20~50ms | 10~20배 |
| 한 JVM 안에서 케이스마다 새 클래스로더로 `Solution` 로드·호출(static 초기화 확인) | 0.6ms/케이스 | 약 100배 |
| 미리 띄운 Python 프로세스(zygote)에서 케이스마다 `fork` | 1.25ms/케이스 | 약 30배 |
| AppCDS 동적 아카이브 | 오히려 느림 | 채택 안 함(0003 결론 유지) |

## 2. 목표

1. **빠르게**: 프로세스 시작·컴파일 고정 비용을 케이스당 수 ms로.
2. **동시에**: 작업 단위가 아니라 케이스 단위로 코어에 나눈다.
3. **가볍게**: 슬롯당 메모리·프로세스 수를 줄여 같은 호스트에 슬롯을 더 둔다.
4. **안전하게**: 최적화가 격리를 약하게 만들지 않는다. 실행마다 uid·네트워크·자원을 나누는 더 강한 격리를 함께 들인다.
5. **기존 동등성**: 판정이 지금과 같아야 한다. 바뀌는 부분은 그림자 채점(6장)으로 확인한 뒤 켠다.

## 3. 성능 설계

### 3.1 컴파일

- **Java 예열 컴파일러**: runner 안에 `javax.tools.JavaCompiler` JVM을 1~2개 상주시킨다.
  - 사용자 코드를 실행하지 않는 단계지만 입력은 신뢰하지 않는다: 전용 uid, 네트워크 차단, 메모리 상한, 컴파일당 시간 제한, `-proc:none`(애노테이션 처리 끔), 소스 경로는 작업 폴더만.
  - 시간 초과·메모리 초과·N회 컴파일마다 프로세스를 새로 띄운다.
- **컴파일 결과 캐시**: 키 = `sha256(언어, 컴파일러 버전, 코드)`. 코드 실행 직후 같은 코드로 제출하는 흐름이 흔하므로 두 번째부터 컴파일을 건너뛴다. tmpfs에 LRU로 둔다.
- **Python**: 별도 `py_compile` 프로세스를 없애고, 샌드박스 자식 안에서 `compile()`한다(서버 프로세스에서 사용자 소스를 컴파일하지 않는다).

### 3.2 케이스 실행

**Python: zygote + 케이스마다 fork**

- 작업마다 샌드박스 uid로 zygote를 하나 띄우고 하네스·표준 모듈을 미리 import한다.
- 케이스마다 fork → 자식이 제한(4장)을 건 뒤 사용자 코드를 실행 → 종료. 케이스마다 새 프로세스라는 지금 동작이 그대로라 동등성 문제가 없다.
- 자식의 CPU 시간·최대 메모리는 서버가 `wait4` rusage로 잰다(신뢰할 수 있는 측정).

**Java: 작업당 JVM 1개 + 케이스마다 새 클래스로더**

- 작업마다 JVM을 하나 띄우고 케이스마다 새 `URLClassLoader`로 `Solution`을 다시 읽는다. 사용자 static 상태가 케이스마다 초기화된다.
- 케이스 입력은 파이프로 하나씩 보내고, 서버가 케이스마다 바깥 감시 시간(제한 + 여유)을 건다. 넘기면 JVM을 끝내고 시간 초과로 판정한다.
- JVM이 중간에 끝나거나(`System.exit`, 메모리 초과), 케이스 뒤에 사용자 스레드가 남으면 남은 케이스를 새 JVM으로 이어서 돌린다.
- **동등성 차이**: 같은 JVM에서는 JIT가 예열돼 뒤 케이스가 빨라질 수 있다. 그래서
  - 코드 실행(run)은 이 방식을 기본으로 쓴다.
  - 제출(submit)은 같은 방식으로 돌리되, 측정 시간이 제한의 일정 비율(예: 50%)을 넘는 케이스나 감시에 걸린 케이스만 새 JVM에서 다시 재서 그 값을 판정에 쓴다(빠른 경로 + 경계 케이스 정밀 재측정).
- 케이스별 시간은 JVM 안에서 재므로 참고값이다. 판정은 바깥 감시와 정밀 재측정으로 한다(4.2 원칙 2).

### 3.3 동시성
- 한 제출의 케이스들을 **여러 슬롯에 동시에** 보낸다. 제출 하나의 벽시계 시간이 케이스 수에 비례하지 않고 슬롯 수로 나뉜다(히든 200개가 직렬 14초 → 슬롯 8개면 약 2초).
- 동시성 단위는 **OS 프로세스(와 전용 uid·네임스페이스)**다. 경량 스레드가 아니다(이유는 3.4). 케이스마다 자식 프로세스가 생겼다 사라지는 것은 그대로고, 어느 슬롯에서 도는지만 분산한다.
- 슬롯 수 = 코어 수에 맞춘다(과도하게 띄우면 문맥 전환으로 측정 시간이 흔들려 판정이 불안정해진다). CPU 측정이 필요한 효율성 문제는 슬롯을 코어에 **고정(affinity)**해 간섭을 줄인다.

### 3.4 경량 실행(goroutine·가상 스레드) 검토 — 어디까지 쓰고 어디서 멈추는가

"goroutine처럼 가벼운 단위로 돌린다"는 두 층으로 나눠 봐야 한다. **제어 층(일을 나눠 주는 쪽)**과 **실행 층(사용자 코드가 도는 쪽)**은 요구가 정반대다.

**(1) 제어 층 — 경량 동시성이 맞다.**
- 0011의 agent/디스패처는 수백 개의 "작업을 기다리는" I/O 대기가 대부분이다. 여기는 goroutine(또는 Java 가상 스레드, Node의 async)이 이상적이다. 스레드 하나가 OS 프로세스 하나를 감시(`wait4`)하며 수백 개를 값싸게 든다.
- **Go로 agent를 쓰는 선택**: 디스패처·runner 호출·결과 전송은 I/O 중심이라 Go goroutine + 채널이 지금 Node 구현보다 가볍고 단순하다(메모리·GC 부담 작음). 0011에서 agent를 브로커 뒤로 빼기로 했으므로, 그때 **agent만 Go로 다시 쓰는** 선택지를 둔다(계약은 `packages/shared`의 JSON·서명 그대로라 언어를 섞어도 된다). 판정 로직(하네스)은 Java·Python에 남으므로 Go는 오케스트레이션만 맡는다.
- 이 층은 사용자 코드를 돌리지 않으므로 경량 스레드의 "격리 없음"이 문제되지 않는다.

**(2) 실행 층 — 경량 스레드로 사용자 코드를 격리할 수 없다.** 이게 핵심 제약이다.
- goroutine·가상 스레드·그린 스레드는 **한 주소 공간**을 공유한다. 서로 다른 사용자(또는 신뢰 코드와 비신뢰 코드)를 스레드로 나누면:
  - 메모리 격리가 없다 — 한 코드가 다른 코드·하네스의 메모리를 읽는다(히든 유출).
  - uid를 스레드별로 낮출 수 없다(`setuid`는 프로세스 단위). seccomp·네임스페이스·cgroup도 프로세스/스레드 그룹 단위라 케이스별 다른 정책을 못 건다.
  - 자원 제한이 공유된다 — 한 케이스의 메모리 초과·무한 루프·`System.exit`·네이티브 크래시가 **같은 런타임의 다른 모든 케이스를 함께 죽인다**.
  - 강제 종료가 안전하지 않다 — 스레드를 밖에서 죽이면(`Thread.stop`은 폐기, goroutine은 외부 취소 불가) 공유 상태가 깨진다. 무한 루프를 끊을 방법이 프로세스 종료뿐이다.
- 따라서 **서로 다른 신뢰 경계의 코드는 반드시 프로세스로 나눈다.** 경량 스레드는 "한 신뢰 경계 안에서 I/O를 기다리는 일"에만 쓴다.

**(3) 절충 — "가벼운 프로세스"로 OS 비용을 줄인다.** 경량 스레드의 속도를 격리를 지키며 얻는 길:
- **zygote + fork**(3.2): fork는 스레드 생성보다는 무겁지만 새 인터프리터 기동(약 36ms)보다 30배 가볍고(1.25ms), **프로세스 경계는 유지**한다. 경량 스레드의 속도에 가장 가까우면서 격리를 지키는 방법이다.
- **Java 가상 스레드(Project Loom, JDK 21)**: 한 제출의 케이스를 **같은 신뢰 경계로 보고** 한 JVM 안에서 가상 스레드로 병렬 호출하는 것은 가능하다(같은 사용자의 코드끼리이므로 메모리 공유가 격리 위반은 아니다). 하지만 위 (2)의 "한 케이스 크래시가 전체를 죽인다", "static·시간 측정 오염", "밖에서 못 끊는다"가 그대로 남아 **판정 안정성**을 해친다. 그래서 가상 스레드는 실행 층에 쓰지 않고, 케이스 병렬은 3.3(프로세스 분산)으로 한다. 가상 스레드는 제어 층(위 1)에서만.

정리: **제어 층 = 경량(goroutine/가상 스레드) 환영. 실행 층 = 프로세스 격리 유지, "가벼움"은 zygote+fork와 워밍 JVM으로 얻는다.**

### 3.5 언어 범위: C++ 지원, PyPy 미지원 (결정)

**PyPy — 지원하지 않는다(결정).**
- 짧은 함수형 케이스가 대부분이라 JIT가 데워지기 전에 끝나 CPython보다 빠르지 않은 경우가 많다.
- 기존 동등성 기준(CPython 3.13.13)과 표준 라이브러리·재귀·부동소수점 동작이 달라 판정이 어긋날 수 있다.
- 런타임이 하나 더 늘면 이미지·격리·회귀 검사 비용이 그만큼 는다. Python 속도는 zygote(3.2)와 고정 비용 제거로 얻는다.

**C++ — 새 채점 언어로 지원한다(결정).**

| 항목 | 정한 것 |
|---|---|
| 컴파일러 | GCC `g++`. 버전은 맞추려는 채점 환경에 맞춰 빌드 인자로 고정한다(Java·Python과 같은 방식, `docker/runner.Dockerfile`). 표준 `-std=gnu++17`, `-O2`, `-pipe`, 경고는 컴파일 결과에 보여 준다 |
| 모드 | **입출력형부터** 연다(stdin/stdout 비교라 하네스가 거의 없다). 함수형은 아래 하네스·타입 규칙을 정한 뒤 연다 |
| 함수형 하네스 | `class Solution { … solution(...) }`을 호출하는 C++ 하네스. 인자는 runner가 매개변수 타입(`int`, `long long`, `double`, `bool`, `string`, `vector<…>`)에 맞춰 변환하고, 반환값을 JSON으로 직렬화해 runner(바깥)가 비교한다. 큰 정수는 `long long` 범위를 넘으면 입력 오류로 알린다 |
| 타입 비교 | Java와 같은 규칙(bool≠int, 실수 1e-9). C++는 정적 타입이라 반환 타입으로 결정한다 |
| 실행 | 네이티브라 기동이 1ms 수준이다. zygote·워밍이 필요 없고 케이스마다 새 프로세스로 돌린다(동등성·격리 모두 가장 단순) |
| 컴파일 비용 | 수백 ms. 컴파일 결과 캐시(3.1)로 코드 실행 → 제출 흐름의 두 번째 컴파일을 없앤다. `bits/stdc++.h`는 미리 컴파일한 헤더(PCH)로 둔다 |
| 메모리 | JVM과 달리 `RLIMIT_AS`가 정확히 걸린다. 문제 메모리 제한을 그대로 쓴다. 재귀가 깊은 풀이를 위해 스택(`RLIMIT_STACK`)을 메모리 제한과 같게 둔다 |

C++ 보안(4장 위에 더하는 것):
- 언어 차원의 보호가 없어 **OS 격리에 전적으로 기댄다**. 그래서 4장 1~3단계(테스트셋 분리·uid 분리·바깥 판정)와 seccomp 허용 목록이 갖춰진 뒤에 연다.
- **컴파일도 비신뢰 입력 처리다**: 컴파일을 샌드박스 uid·시간·메모리 제한·네트워크 차단 아래에서 한다. `#include`로 시스템 파일을 읽어 오류 메시지에 내보내는 경로를 막기 위해 include 경로를 표준 라이브러리로 제한하고, 컴파일 오류 메시지에서 작업 폴더 밖 경로·내용을 잘라 낸다. 컴파일러 플래그는 사용자가 바꿀 수 없다.
- 실행 파일은 작업 폴더(tmpfs)에만 만들고, 사용자 코드가 다른 실행 파일을 쓰거나 실행하지 못하게 `execve`를 seccomp로 막는다(첫 실행 뒤).
- 정의되지 않은 동작(UB)으로 인한 비결정성은 다른 저지와 같이 사용자 책임으로 둔다.

| 언어 | 상태 | 핵심 |
|---|---|---|
| Python(CPython 3.13.13) | 지원 | zygote + fork로 경량화 |
| Java(OpenJDK 21.0.2) | 지원 | 예열 컴파일 + 작업당 JVM |
| C++(GCC) | **추가 지원** | 4장 격리 뒤, 입출력형 → 함수형 |
| PyPy | **미지원** | 결정(위) |
| Go | 사용자 언어 아님 | 0011 agent(제어 층) 구현 후보 |

## 4. 보안 설계 (코드 인젝션·탈옥·히든 유출·오남용)

지금 통제(0001): 인터넷 차단 `internal` 네트워크, 루트 FS 읽기 전용, 쓰기는 `/tmp` tmpfs, 사용자 코드는 uid 10001 + `setsid` + rlimit(CPU·FSIZE·NOFILE·NPROC·Python 주소 공간) + 10초, 호스트 포트 없음, capability 6개.

위협 모델: 공격자는 로그인한 사용자이며 임의의 Java·Python·C++ 코드를 제출할 수 있다. 막아야 할 것과 통제:

| 위협 | 지켜야 할 속성 | 통제 |
|---|---|---|
| 히든 테스트셋·정답 노출 | 비신뢰 코드는 자기 케이스의 인자 외 어떤 테스트 데이터도 읽을 수 없다. 제출 결과로 히든 데이터가 나가지 않는다 | 4.1·4.2 |
| 다른 사용자·다른 작업 간섭 | 동시에 도는 코드끼리 파일·프로세스·신호로 닿지 않는다 | 4.3 |
| 판정 조작 | 시간·메모리·정답 비교는 비신뢰 코드 바깥에서 만든 값으로만 한다 | 4.4 |
| 탈옥·외부 접근 | 네트워크·runner API·호스트 커널에 닿는 경로를 최소화한다 | 4.3·4.5 |
| 코딩테스트 목적 밖 사용 | 채굴·스캔·장시간 연산·fork 폭탄이 다른 사용자에게 영향을 주지 못한다 | 4.5 |

### 4.1 받는 쪽: 결과에서 히든 정보 지우기
- 제출(submit)은 이미 `actual=null, stdout='', stderr`는 2000자로 자른다(judge `trimResult`). 유지.
- **추가**: 제출의 `stderr`도 히든 입력·기댓값을 담을 수 있다. 제출에서는 stderr를 **표준 오류 유형으로 치환**한다(런타임 에러 / 메모리 초과 / 컴파일 에러 — 사용자 코드 줄 번호까지만). 원문은 agent 로그에만. `packages/shared`의 제출 결과 stderr를 열거형으로 바꾼다. 화면(`ResultPanel.tsx`)은 제출에서 통과/실패·시간·메모리·점수만 보여 주므로 영향이 작다.
- 코드 실행(run)은 보이는 케이스만 쓰므로 지금처럼 전체 표시.

### 4.2 히든 테스트셋을 사용자 코드에서 숨기기
- 테스트셋 캐시 디렉터리를 **사용자 코드가 도는 마운트 네임스페이스 밖**에 둔다. 실행기(신뢰)가 읽어 케이스 인자만 자식에게 파이프/인자로 주고, 자식은 테스트셋 파일에 접근할 수 없다.
- 두 원칙: **① 비신뢰 코드에는 그 케이스의 인자만 준다. ② 채점에 쓰는 값(시간·메모리·정답 비교)은 비신뢰 코드 바깥에서 만든다.**

### 4.3 실행마다·제출마다 격리
- **A안(지금 Docker 강화, 먼저)**: 제한적 `seccomp` 프로파일(socket 생성·`ptrace`·새 네임스페이스·모듈 로드 차단), 케이스/제출마다 **uid 풀**에서 다른 uid 할당(동시에 도는 코드끼리 못 봄, `NPROC`가 uid별로 분리됨), 작업 폴더를 자식 전용 네임스페이스 `/tmp`로 bind.
- **B안(샌드박스 엔진, 0003 2단계 재개)**: 실행마다 cgroup v2로 메모리·CPU·PID를 재고 seccomp를 거는 전용 샌드박스.
  - **nsjail**: 가볍다(프로세스 단위, 거의 0 오버헤드). 비권한 Docker 안에서는 user namespace·cgroup v2 위임이 막혀 완화가 필요 — 지금의 최소 권한 컨테이너와 상충. **실행 호스트를 분리하는 0011 Tier 1(전용 노드)에서 적합.**
  - **gVisor(runsc)**: 커널 노출을 크게 줄이나 fork·exec·syscall이 많은 채점에 오버헤드가 크다(여러 벤치 15~38%). 워밍(3.2)으로 프로세스 수를 줄이면 상쇄.
  - **채택**: Tier 0은 A안으로 당장 강화. 실행 호스트를 분리하는 Tier 1부터 nsjail 1순위, 커널 노출을 더 줄여야 하면 gVisor. 어느 쪽이든 `runner/selftest.py` 격리 검사를 늘려 CI `docker` 잡에서 통과시킨다(AGENTS.md 규칙).

### 4.4 시간·자원 판정을 바깥에서
- 함수형 시간 초과를 하네스의 `timeMs`가 아니라 **실행기가 벽시계(`run_proc`의 `time_ms`)로 잰 값**으로 판정한다. 하네스 `timeMs`는 참고 표시만.
- 메모리는 `ru_maxrss`(바깥 측정) 유지. CPU 시간(`RLIMIT_CPU`)과 벽시계 제한을 함께 둬 `sleep`·바쁜 대기를 모두 잡는다.

### 4.5 오남용 방지
- 네트워크 없음 유지(`internal`) + seccomp로 socket 차단(이중).
- fork 폭탄: `RLIMIT_NPROC` + 컨테이너 `pids_limit` + cgroup PID 제한, uid 풀로 사용자별 집계.
- 자원 고갈·채굴: CPU·벽시계·메모리·출력 상한(지금 있음) + 제출당 600초 예산 + 0011 받아들이기 제어(사용자별 동시 실행 상한).
- 디스크·출력 폭탄: tmpfs 상한·`RLIMIT_FSIZE`·출력 상한(지금 있음), 제출 사이 작업 폴더 삭제(지금 `rmtree`).

### 4.6 Java·네이티브 보안 메모
- Security Manager는 JDK 24에서 영구 비활성화(JEP 486). **JVM 내부 샌드박스에 의존하지 않고 OS 격리(4.3)에만 의존**한다(지금도 그렇다). 워밍 JVM은 "한 JVM이 여러 사용자를 가둔다"에 기대지 않고, JVM 자체를 OS 샌드박스 안에 두고 제출마다 버린다.
- 리플렉션으로 하네스·실행기 내부에 닿는 것은 격리된 클래스로더로 줄이되, 최종 방어선은 OS 격리다.
- C++ 등 네이티브 언어는 언어 가드가 없으므로 seccomp 기본 거부 + 허용 목록이 특히 중요하다(4.3 B).

## 5. 기존 동등성 지키기: 그림자 채점
- **그림자 모드**: 새 실행기(워밍·C++ 판정 등)와 지금 실행기를 같은 제출에 둘 다 돌려 결과를 비교·기록하고, 사용자에게는 지금 결과만 보여 준다. 충분히 일치하면(예: 1주 불일치 0건) 종류·언어별로 새 방식을 기본으로 바꾼다.
- `runner/selftest.py`에 격리·판정 회귀 검사를 더하고 CI `docker` 잡에서 통과시킨다.
- e2e(`e2e/tests/api/isolation.spec.ts`, `judge.spec.ts`)에 유출·탈옥·시간 위조 회귀 케이스를 더한다. 공개 저장소이므로 "무엇을 막는지"만 주석으로 적고 민감한 기법 설명은 쓰지 않는다.

## 6. 단계 (0011 Tier와 맞춤)

| 단계 | 내용 | 시점 |
|---|---|---|
| 1. 받는 쪽 유출 차단 | 제출 결과 stderr 유형 치환(4.1), 계약 변경. 위험 작음 | Tier 0, **먼저** |
| 2. Docker 격리 강화 | seccomp·uid 풀·마운트 분리로 테스트셋 숨김(4.2·4.3 A), selftest 보강 | Tier 0, **먼저** |
| 3. 판정을 바깥에서 | 시간·메모리 판정을 실행기 측정값으로(4.4) | Tier 0, **먼저** |
| 4. Java 예열 컴파일 + 컴파일 캐시 | `javax.tools` 서비스(3.1), 그림자 비교 | Tier 0~1 |
| 5. 케이스 단위 동시 실행 | 한 제출의 케이스를 여러 슬롯·코어에 분산(3.3) | Tier 1 |
| 6. 워밍 실행기(Python zygote·Java 작업당 JVM) | 전용 샌드박스 안에서(3.2, 4.3 B). 실행 호스트 분리 뒤 | Tier 1~2 |
| 7. agent를 경량 동시성으로 | 제어 층을 Go goroutine/가상 스레드로(3.4-1). 선택 | Tier 1~2 |
| 8. C++ 추가 | 입출력형 → 함수형(3.5). PyPy는 미지원 | 1~3단계 완료 뒤 |

1~3은 성능과 무관한 **보안 수정이라 가장 먼저** 한다. 각 단계는 그림자 채점(5장)으로 기존 동등성을 확인한 뒤 켠다.

## 7. 결정이 필요한 것
1. 제출 결과 stderr를 완전히 숨길지, "사용자 코드 줄 번호까지"는 보여 줄지(유출 위험 대 디버깅 편의).
2. 실행 호스트를 Docker 안(nsjail 제약)에 둘지 전용 노드로 둘지 — 0011 Tier 1 공급처와 함께.
3. 워밍·agent 재작성(6·7단계)을 들일 만큼 초당 제출 수가 커질지 — 0011 Tier 0 측정 뒤 결정. 안 커지면 1~5단계(특히 1~3 보안)로 충분.
4. C++ 컴파일러 버전(맞추려는 채점 환경)과 함수형 C++의 타입 범위.
