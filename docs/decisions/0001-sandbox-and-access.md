# 0001. 코드 실행 격리와 접근 제어

- 날짜: 2026-10-21
- 상태: 채택

## 배경

인터넷에 공개된 주소에서 임의 코드를 실행한다. 사용자는 나 혼자지만, 키 유출·세션 탈취·코드 실수(무한 루프, 메모리 폭주, 포크 폭탄)에도 서버(pahidc, 다른 서비스와 공유)가 버텨야 한다. 저장소는 공개다.

## 결정

1. **접근**: stock과 같은 Ed25519 개인키 로그인. 공개키만 서버에 두고, 세션은 SQLite에 저장해 로그아웃 시 무효화한다. → [0002](0002-password-login.md)에서 비밀번호 로그인으로 대체.
2. **실행 분리**: 사용자 코드는 api가 아니라 별도 `runner` 컨테이너에서만 실행한다.
   - Docker 소켓을 api에 주지 않는다(요청마다 컨테이너를 띄우는 방식은 소켓 = 호스트 root라 채택하지 않음).
   - runner는 `internal: true` 네트워크 → 인터넷·호스트 포트 없음.
   - 읽기 전용 루트 파일시스템 + `/tmp` tmpfs, 메모리 1.5GB, CPU 2, PID 512, `no-new-privileges`.
3. **프로세스 격리**: runner 서버는 root(최소 capability)로 돌며 작업 폴더를 만들고, 사용자 코드는 `setsid` + `setuid(10001)` + rlimit(CPU, FSIZE, NOFILE, NPROC, Python은 AS) + 10초 벽시계 제한으로 실행한다. 사용자 코드는 서버 프로세스에 시그널을 보내거나 실행기 파일을 바꿀 수 없다(`selftest.py`의 격리 검사).
4. **공개 저장소의 self-hosted runner**: 배포 잡은 `push: main`/`workflow_dispatch` + 저장소·브랜치 조건에서만 돈다. 외부 기여자 PR 워크플로는 항상 승인이 필요하고, `production` 환경은 `main`에서만 쓸 수 있다.

## 결과

- 함수형 Java는 케이스마다 JVM을 새로 띄워 케이스당 0.3~0.5초가 더 든다(기존와 같은 방식).
- Cloudflare 응답 제한(100초) 때문에 요청 전체 실행을 80초로 끊고 나머지 케이스는 `skipped`로 표시한다.
- gVisor 같은 커널 수준 격리는 쓰지 않는다. 단일 사용자 + 인증 뒤에 있으므로 컨테이너·uid 격리로 충분하다고 본다.
